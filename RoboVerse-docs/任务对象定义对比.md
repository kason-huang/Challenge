# RoboTwin vs RoboVerse 任务对象定义对比

## 概述

本文档对比 RoboTwin 和 RoboVerse 两个框架中 Task 对象的设计哲学和关键差异，帮助理解它们不同的应用场景和设计目标。

---

## 一、设计哲学对比

### 1.1 根本目标

| 维度 | RoboTwin | RoboVerse |
|-------|-----------|-----------|
| **设计目标** | 专家轨迹生成系统 | RL 训练与评测环境 |
| **应用场景** | 数据收集、演示录制 | 策略学习、强化学习 |
| **核心问题** | "机器人应该做什么？" | "策略应该如何观察和动作？" |
| **数据流** | 专家动作 → 环境状态 → 语言指令 | 状态 → 动作 → 奖励 → 下一状态 |
| **兼容标准** | 非标准 Gym 环境 | 标准 Gymnasium 环境 |

### 1.2 架构层次对比

```
RoboTwin 架构：
┌─────────────────────────────────────┐
│ Base_Task (非标准 Gym）        │
│ ├─ setup_demo()     场景初始化 │
│ ├─ load_actors()    物体创建   │
│ ├─ play_once()      专家动作序列 │
│ └─ check_success()  成功条件   │
│                                    │
│ → info["info"]                 │
│   (用于指令生成)               │
└─────────────────────────────────────┘

RoboVerse 架构：
┌─────────────────────────────────────┐
│ BaseTaskEnv (标准 Gym）      │
│ ├─ ScenarioCfg      场景配置   │
│ ├─ _get_initial_states()  初始状态 │
│ ├─ _terminated()    成功条件    │
│ ├─ _reward()        奖励函数   │
│ ├─ _observation_space() 观测空间  │
│ └─ step()          标准step   │
│                                    │
│ → TensorState                 │
│   (统一状态表示)              │
└─────────────────────────────────────┘
```

## 二、RoboTwin 的 Task 对象

### 2.1 对象结构

```python
class stack_bowls_two(Base_Task):
    """RoboTwin 任务：堆叠两个碗"""

    # ========================
    # 关键属性
    # ========================
    
    # 场景配置（不是 observation/action_space）
    # 这些在 setup_demo() 中动态设置
    self.info = dict()
    self.plan_success = True
    self.step_lim = 900
    self.traj_filepath = None

    # 任务对象
    self.bowl1 = create_actor(...)
    self.bowl2 = create_actor(...)
    self.bowl1_target_pose = np.array([0, -0.1, 0.76])
    self.quat_of_target_pose = [0, 0.707, 0.707, 0]

    # ========================
    # 核心方法
    # ========================
    
    def setup_demo(self, **kwargs):
        """初始化任务环境"""
        super()._init_task_env_(**kwargs)
        self.load_actors()

    def load_actors(self):
        """加载任务所需的物体"""
        # 创建物体、设置禁止区域、定义目标位置
        self.bowl1 = create_actor(...)
        self.bowl2 = create_actor(...)

    def play_once(self):
        """
        执行一次专家演示

        Returns:
            self.info (dict): 包含场景信息
        """
        # 执行专家动作序列
        arm_tag1 = self.move_bowl(self.bowl1, self.bowl1_target_pose)
        arm_tag2 = self.move_bowl(self.bowl2, self.bowl1.get_pose().p + [0, 0, 0.05])

        # 关键：返回 info 字典
        self.info["info"] = {
            "{A}": f"002_bowl/base3",      # 物体类型（用于指令生成）
            "{B}": f"002_bowl/base3",      # 物体类型
            "{a}": str(arm_tag1),             # 使用的机械臂
            "{b}": str(arm_tag2),             # 使用的机械臂
        }
        return self.info

    def check_success(self):
        """检查任务是否成功"""
        bowl1_pose = self.bowl1.get_pose().p
        bowl2_pose = self.bowl2.get_pose().p

        # 检查空间关系
        target_height = [0.74 + self.table_z_bias, 0.77 + self.table_z_bias]
        eps = np.array([0.02, 0.02])

        condition1 = np.all(abs(bowl1_pose[:2] - bowl2_pose[:2]) < eps)
        condition2 = np.all(np.array([bowl1_pose[2], bowl2_pose[2]]) - target_height < eps)
        condition3 = self.is_left_gripper_open() and self.is_right_gripper_open()

        return condition1 and condition2 and condition3
```

### 2.2 关键信息分析

RoboTwin 的 Task 对象包含以下关键信息：

| 信息类型 | 字段/属性 | 示例 | 作用 |
|----------|------------|-------|------|
| **物体引用** | `self.bowl1`, `self.bowl2` | `create_actor()` 返回的对象 | 可查询状态、位置、姿态 |
| **目标位置** | `self.bowl1_target_pose` | `np.array([x, y, z])` | 定义任务目标 |
| **场景参数** | `self.info["info"]` | `{"{A}": "002_bowl/base3", ...}` | 用于指令生成 |
| **成功条件** | `check_success()` 方法 | 空间关系检查 | 判断任务完成 |
| **步数限制** | `self.step_lim` | `900` | 控制执行时长 |
| **计划标志** | `self.plan_success` | `True/False` | 专家轨迹是否成功规划 |

### 2.3 为什么不需要 observation_space/action_space？

**核心原因**：RoboTwin 不是 RL 环境，而是专家轨迹生成系统

1. **非 Gymnasium 环境**
   - RoboTwin 继承自 `Base_Task(gym.Env)`，但没有实现标准的 `step(action)` 接口
   - 不需要遵循 Gymnasium 的空间定义规范

2. **高层动作原语**
   - 使用特定方法如 `grasp_actor()`, `place_actor()`，而不是通用动作空间
   - 这些方法内部直接操作机器人的关节和夹爪
   - 动作参数通过参数传递，而非批量张量

3. **数据收集导向**
   - 主要用途是生成专家演示数据
   - 观测在数据收集时通过 `get_obs()` 直接获取（RGB、深度、关节位置）
   - 不需要明确定义观测空间，因为观测结构是固定的

4. **指令生成导向**
   - `info["info"]` 字典用于后续的语言指令生成
   - 占位符 `{A}`, `{B}`, `{a}`, `{b}` 被替换为实际的物体描述和机械臂名称
   - 这是一个数据预处理阶段，而非训练循环的一部分

5. **固定的数据格式**
   - RoboTwin 有确定的数据格式：RGB、深度、点云、端部位姿、关节位置
   - 观测结构由基类固定提供，无需自定义

## 三、RoboVerse 的 Task 对象

### 3.1 对象结构

```python
@register_task("libero_90.kitchen_scene1_put_black_bowl_on_plate")
class LiberoKitchen1PutBowlOnPlateTask(BaseTaskEnv):
    """RoboVerse 任务：将黑碗放在盘子上"""

    # ========================
    # 关键属性
    # ========================
    
    # 场景配置（类变量，核心设计）
    scenario = ScenarioCfg(
        objects=[
            RigidObjCfg(
                name="akita_black_bowl",
                usd_path="assets/akita_black_bowl.usd",
                urdf_path="assets/akita_black_bowl.urdf",
                mjcf_path="assets/akita_black_bowl.xml",
                physics=PhysicStateType.RIGIDBODY,
            ),
            RigidObjCfg(
                name="plate",
                usd_path="assets/plate.usd",
                urdf_path="assets/plate.urdf",
                mjcf_path="assets/plate.xml",
                physics=PhysicStateType.RIGIDBODY,
            ),
            ArticulationObjCfg(
                name="wooden_cabinet",
                fix_base_link=True,
                usd_path="assets/wooden_cabinet.usd",
            ),
        ],
        robots=["franka"],
    )

    max_episode_steps = 300
    task_desc = "Put the black bowl on the plate"

    # ========================
    # 核心方法
    # ========================
    
    def _get_initial_states(self) -> list[dict]:
        """
        返回每个环境的初始状态

        Returns:
            list[dict]: 每个环境的完整状态
        """
        return [
            {
                "objects": {
                    "akita_black_bowl": {
                        "pos": torch.tensor([0.5, 0.0, 0.3]),
                        "rot": torch.tensor([1.0, 0.0, 0.0, 0.0]),
                    },
                    "plate": {
                        "pos": torch.tensor([0.0, -0.1, 0.74]),
                        "rot": torch.tensor([0.999067, 0.0000006, 0.0000009, 0.043198]),
                    },
                },
                "robots": {
                    "franka": {
                        "pos": torch.tensor([0.0, 0.0, 0.0]),
                        "rot": torch.tensor([1.0, 0.0, 0.0, 0.0]),
                        "joint_pos": {
                            "panda_joint1": 0.0,
                            "panda_joint2": -0.5,
                            "panda_joint3": 0.0,
                            ...
                        },
                    },
                },
                "cameras": {},
                "extras": {},
            }
            for _ in range(self.num_envs)
        ]

    def _terminated(self, states: TensorState) -> torch.Tensor:
        """
        检查任务是否完成

        Args:
            states: TensorState - 统一状态表示
        """
        bowl_pos = states.objects["akita_black_bowl"].root_state[:, 0:3]
        plate_pos = states.objects["plate"].root_state[:, 0:3]

        # 计算空间关系
        xy_distance = torch.norm(bowl_pos[:, 0:2] - plate_pos[:, 0:2], dim=-1)
        height_diff = bowl_pos[:, 2] - plate_pos[:, 2]
        height_valid = (height_diff > 0) & (height_diff < 0.03)

        # 检查条件
        range_threshold = 0.06
        xy_close = xy_distance < range_threshold
        is_on_plate = xy_close & height_valid

        return is_on_plate

    def _observation_space(self) -> gym.spaces.Space:
        """返回观测空间"""
        return gym.spaces.Box(low=-np.inf, high=np.inf, shape=(obs_dim,))

    def _action_space(self) -> gym.spaces.Space:
        """返回动作空间"""
        return gym.spaces.Box(low=-1.0, high=1.0, shape=(action_dim,))

    def step(self, actions: torch.Tensor):
        """执行一步仿真"""
        # 调用父类 step()
        obs, reward, terminated, time_out, info = super().step(actions)
        return obs, reward, terminated, time_out, info

    def reset(self, states=None, env_ids=None) -> tuple[Obs, Info]:
        """重置环境"""
        obs, info = super().reset(states, env_ids)
        return obs, info
```

### 3.2 关键信息分析

RoboVerse 的 Task 对象包含以下关键信息：

| 信息类型 | 字段/属性 | 示例 | 作用 |
|----------|------------|-------|------|
| **场景配置** | `scenario` (类变量) | `ScenarioCfg(objects=..., robots=...)` | 定义所有静态配置 |
| **初始状态** | `_get_initial_states()` | 返回包含物体/机器人状态的字典列表 | 设置每个环境的初始状态 |
| **成功条件** | `_terminated()` | 返回布尔张量 [num_envs] | 判断任务完成 |
| **奖励函数** | `_reward()` | 返回奖励张量 [num_envs] | 计算学习信号 |
| **观测空间** | `_observation_space()` | 返回 `gym.spaces.Box` | 定义观测维度 |
| **动作空间** | `_action_space()` | 返回 `gym.spaces.Box` | 定义动作维度 |
| **最大步数** | `max_episode_steps` | `300` | 控制训练循环 |

### 3.3 为什么必须定义 observation_space/action_space？

**核心原因**：RoboVerse 是标准 RL 环境，必须符合 Gymnasium 规范

1. **标准 Gymnasium 接口**
   - RoboVerse 继承自 `BaseTaskEnv`，后者继承自 `gym.Env`
   - 必须实现 `observation_space` 和 `action_space` 属性
   - 必须实现标准的 `step(action)` 和 `reset()` 方法

2. **策略交互需求**
   - RL 算法需要知道观测的形状和维度
   - 策略需要知道动作的形状和取值范围
   - `observation_space` 和 `action_space` 提供了这些接口契约

3. **批量并行支持**
   - RoboVerse 原生支持批量环境（`num_envs=10`）
   - 所有观测、动作、奖励都是批量张量 `[num_envs, ...]`
   - 需要明确定义每个维度的形状

4. **TensorState 统一表示**
   - RoboVerse 使用 `TensorState` 作为统一的仿真状态访问接口
   - 观测函数需要从 `TensorState` 中提取数据并组合成向量
   - `_observation_space()` 定义了如何将 `TensorState` 转换为观测向量

5. **学习反馈机制**
   - `_reward()` 函数提供奖励信号
   - `_terminated()` 函数提供成功/失败信号
   - 这些是策略学习的基础信号

6. **兼容性**
   - 必须兼容各种 RL 算法（PPO, SAC, TD3 等）
   - 这些算法依赖标准的 Gymnasium 接口

## 四、两种任务对象的详细对比

### 4.1 对象继承关系

```
RoboTwin:
Base_Task (gym.Env 但非标准)
    ├─ setup_demo()      # 非标准方法
    ├─ load_actors()    # 自定义方法
    ├─ play_once()       # 自定义方法
    └─ check_success()   # 自定义方法

RoboVerse:
BaseTaskEnv (gym.Env，标准接口)
    ├─ ScenarioCfg        # 场景配置（类变量）
    ├─ _get_initial_states()  # 标准接口
    ├─ _terminated()      # 标准接口
    ├─ _reward()           # 标准接口
    ├─ _observation_space()  # 标准接口
    ├─ _action_space()      # 标准接口
    ├─ step()             # 标准接口
    └─ reset()            # 标准接口
```

### 4.2 核心方法对比

| 方法 | RoboTwin | RoboVerse | 对比 |
|------|----------|-----------|------|
| **环境初始化** | `setup_demo(**kwargs)` | `__init__(self, scenario, device)` | RoboTwin 动态初始化；RoboVerse 配置驱动 |
| **场景配置** | 在 `load_actors()` 中硬编码 | `scenario = ScenarioCfg(...)` | RoboTwin 分散配置；RoboVerse 集中配置 |
| **初始状态** | 无（直接在物体上操作） | `_get_initial_states()` 返回状态字典 | RoboTwin 对象状态隐含；RoboVerse 显式管理 |
| **动作执行** | `play_once()` 使用高层 API | `step(actions)` 批量动作 | RoboTwin 单次演示；RoboVerse 批量训练 |
| **状态访问** | `actor.get_pose()` 直接访问对象 | `states.objects[name].root_state` | RoboTwin 直接属性；RoboVerse 统一接口 |
| **成功判断** | `check_success()` 返回 bool | `_terminated(states)` 返回 Tensor[bool] | RoboTwin 单环境；RoboVerse 批量 |
| **信息输出** | `info["info"]` 字典 | `info` 字典包含 `privileged_observation` | RoboTwin 用于指令生成；RoboVerse 用于训练 |
| **观测空间** | ❌ 不定义 | ✅ 必须定义 | RoboTwin 固定格式；RoboVerse 可定制 |
| **动作空间** | ❌ 不定义 | ✅ 必须定义 | RoboTwin 高层 API；RoboVerse 批量张量 |

### 4.3 状态管理对比

**RoboTwin 状态管理**：
```python
# 状态分散在各个对象上
self.bowl1 = create_actor(...)  # 直接对象引用
self.bowl1_target_pose = np.array(...)  # 直接 numpy 数组

# 访问时
pose = self.bowl1.get_pose().p  # 直接调用对象方法
```

**RoboVerse 状态管理**：
```python
# 状态统一在 TensorState 中
states = env.reset()

# 访问时
bowl_pos = states.objects["akita_black_bowl"].root_state[:, 0:3]
# 这返回的是 torch.Tensor [num_envs, 3]
robot_joint_pos = states.robots["franka"].joint_pos  # [num_envs, num_joints]
```

## 六、TensorState 深入解析

### 6.1 TensorState 结构详解

```python
states = env.reset()

# 物体状态
states.objects["target"]           # ObjectState
  ├─ root_state: [N, 13]  # [pos(3), quat(4), lin_vel(3), ang_vel(3)]
  └─ joint_pos: [N, num_joints]  # 仅关节物体
  └─ body_names: List[str]

# 机器人状态
states.robots["franka"]          # RobotState
  ├─ root_state: [N, 13]     # [pos(3), quat(4), lin_vel(3), ang_vel(3)]
  ├─ joint_pos: [N, num_joints]  # 关节位置
  ├─ joint_vel: [N, num_joints]  # 关节速度
  ├─ joint_pos_target: [N, num_joints]  # 目标关节位置（轨迹跟踪）
  ├─ joint_vel_target: [N, num_joints]  # 目标关节速度
  └─ body_names: List[str]          # 机器人身体名称列表

# 相机状态
states.cameras["head_camera"]    # CameraState
  ├─ rgb: [N, H, W, 3]       # RGB 图像
  ├─ depth: [N, H, W]         # 深度图
  ├─ pos: [N, 3]             # 相机位置
  └─ quat_world: [N, 4]         # 相机朝向

# 自定义数据
states.extras                       # Dict[str, Any]  # 额外信息
```

### 6.2 为什么 RoboVerse 需要 TensorState？

**关键设计决策**：统一状态访问接口

1. **多仿真器抽象**
   - 不同仿真器（Isaac Lab, MuJoCo, SAPIEN）有不同的状态表示
   - RoboVerse 需要一个统一的接口来访问这些不同格式的状态

2. **批量并行**
   - 所有操作都是批量化的 `[num_envs, ...]`
   - 无法直接访问 Python 对象（如 `self.bowl1`）
   - 需要通过统一的张量接口访问状态

3. **状态组合**
   - 需要同时访问多个物体、机器人、相机的状态
   - 需要支持 `env.reset(env_ids=[0, 2, 5])` 部分重置
   - TensorState 提供了这种批量、分层、统一的状态表示

4. **性能优化**
   - 张量操作比对象方法调用快（GPU 加速）
   - 避免了 Python 循环的开销

5. **数据流清晰**
   - 状态通过 `TensorState` 统一获取和传递
   - 观测函数从 `TensorState` 提取数据并组合
   - 明确的数据流：`TensorState → Observation → Action → Reward/Termination`

## 七、任务定义模式对比

### 7.1 RoboTwin 模式

```python
# 1. 创建物体
self.bowl1 = create_actor(scene=self, pose=..., modelname="002_bowl", model_id=3)

# 2. 定义目标
self.bowl1_target_pose = np.array([0, -0.1, 0.76])

# 3. 执行专家动作
arm_tag = self.move_bowl(self.bowl1, self.bowl1_target_pose)

# 4. 返回场景信息
self.info["info"] = {
    "{A}": "002_bowl/base3",
    "{B}": "002_bowl/base3",
    "{a}": str(arm_tag),
}
```

**特点**：
- 直接操作对象
- 简单直观
- 适合演示录制
- 不适合批量训练

### 7.2 RoboVerse 模式

```python
# 1. 定义场景配置
scenario = ScenarioCfg(
    objects=[
        RigidObjCfg(
            name="akita_black_bowl",
            usd_path="assets/akita_black_bowl.usd",
            physics=PhysicStateType.RIGIDBODY,
        ),
        ...
    ],
    robots=["franka"],
)

# 2. 返回初始状态
def _get_initial_states(self) -> list[dict]:
    return [{
        "objects": {
            "akita_black_bowl": {
                "pos": torch.tensor([0.5, 0.0, 0.3]),
                "rot": torch.tensor([1.0, 0.0, 0.0, 0.0]),
            },
        },
        ...
    } for _ in range(num_envs)]

# 3. 定义观测空间
def _observation_space(self) -> gym.spaces.Space:
    # 例如：关节位置 + 物体位置 + RGB 图像
    obs_dim = calculate_total_dim()
    return gym.spaces.Box(low=-np.inf, high=np.inf, shape=(obs_dim,))

# 4. 定义成功条件
def _terminated(self, states: TensorState) -> torch.Tensor:
    bowl_pos = states.objects["akita_black_bowl"].root_state[:, 0:3]
    plate_pos = states.objects["plate"].root_state[:, 0:3]
    
    xy_distance = torch.norm(bowl_pos[:, 0:2] - plate_pos[:, 0:2], dim=-1)
    height_diff = bowl_pos[:, 2] - plate_pos[:, 2]
    
    xy_close = xy_distance < 0.06
    height_valid = (height_diff > 0) & (height_diff < 0.03)
    
    return xy_close & height_valid  # 返回 [N,] 布尔张量
```

**特点**：
- 配置驱动
- 批量张量操作
- 适合 RL 训练
- 支持多仿真器
- 性能优化

## 八、总结

### 8.1 关键差异总结表

| 维度 | RoboTwin | RoboVerse |
|-------|-----------|-----------|
| **框架类型** | 专家轨迹生成系统 | RL 训练环境 |
| **继承基类** | `Base_Task` (非标准 Gym) | `BaseTaskEnv` (标准 Gym) |
| **场景配置** | 在 `load_actors()` 中设置 | `scenario = ScenarioCfg(...)` 类变量 |
| **状态管理** | 分散在对象属性上 | 统一在 `TensorState` 中 |

| **成功判断** | `check_success()` 单环境 bool | `_terminated(states)` 批量 Tensor[bool] |
| **观测空间** | ❌ 不定义（固定格式） | ✅ 必须定义（可定制） |
| **动作空间** | ❌ 不定义（高层 API） | ✅ 必须定义（批量张量） |
| **信息输出** | `info["info"]` 指令参数 | `info` 包含训练信号（reward, terminated） |
| **并行支持** | ❌ 单环境串行 | ✅ 批量并行（`num_envs=10`） |
| **GPU 支持** | ⚠️ 有限（内部变量） | ✅ 原生 CUDA 批量 |
| **主要用途** | 数据收集、演示录制 | RL 训练、评测 |
| **语言条件** | ✅ 内置（info["info"] → 指令） | ⚠️ 需要集成外部 LLM |
| **多仿真器** | ❌ 固定 SAPIEN | ✅ 支持 6+ 种 |
| **跨数据集** | ❌ 专用 | ✅ 支持 10+ 个外部任务集 |
| **兼容性** | ⚠️ 非标准 Gym | ✅ 标准 Gymnasium |

### 8.2 设计哲学总结

**RoboTwin 的设计哲学**：
- "我应该让机器人做什么？"（命令式）
- 关注专家演示的质量和多样性
- 适合人类遥操作和模仿学习
- 简化数据生成流程

**RoboVerse 的设计哲学**：
- "策略应该如何观察和动作？"（学习式）
- 关注标准接口和批量性能
- 适合强化学习和大规模训练
- 提供统一的多任务、多仿真器基准

### 8.3 适用场景选择指南

|-------|---------|---------|
| 生成专家轨迹 | RoboTwin | 简单直观、专用硬件 |

## 九、如何选择？

### 9.1 根据需求选择

**问题 1：我要收集专家演示数据**
- **选择**：RoboTwin
- **原因**：

  - 简单直观的任务定义
  - 内置的语言指令系统
  - 专注于数据质量和多样性

- **选择**：RoboVerse

  - 批量并行支持（GPU 加速）
  - 统一的观测/动作空间定义
  - 兼容各种 RL 算法（PPO, SAC, TD3 等）
  - 内置的奖励和成功判断机制

  - 一致的接口，便于比较不同仿真器性能

- **原因**：

## 十、结论

两个框架代表了**两种不同的设计哲学**：

- **RoboTwin**：专注于专家轨迹生成和演示，使用高层 API，简化了数据收集流程
- **RoboVerse**：专注于 RL 训练和评测，使用标准 Gymnasium 接口，提供了批量优化和多仿真器支持

选择哪个框架取决于你的**主要目标**：

- 如果目标是**收集高质量专家数据**用于后续训练 → RoboTwin 更合适
- 如果目标是**训练 RL 策略**或进行大规模实验 → RoboVerse 更合适
- 如果需要**跨平台测试**或多数据集基准 → RoboVerse 更合适

两种框架可以结合使用：用 RoboTwin 生成专家数据，在 RoboVerse 中训练策略。
